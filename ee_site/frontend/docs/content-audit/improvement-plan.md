## 5. Правила подтверждения и публикации документов

Перед новой публикацией паспортов/опросников/схем/протоколов:

- Установить полезность: какой конкретный вопрос из матрицы документ закрывает; не выкладывать большой архив ради «экспертности».
- Проверить владельца/источник, применимость к изделию/исполнению, дату/версию, актуальность требований и читаемость единиц. Пример снабдить пометкой «образец», а не объявлять обязательным пакетом.
- Предпочесть текстовый PDF с выделяемым текстом и понятными подписями плюс краткую HTML-аннотацию. Если есть только скан, подготовить читаемую проверенную текстовую выдержку; OCR проверяет инженер.
- Проверить имена/телефоны/email/подписи, штампы, номера заказов, договоры, цены, планы объекта, схемы доступа и технологические секреты; метаданные/имена файлов/EXIF тоже могут раскрывать сведения.
- Получить разрешение на название заказчика, узнаваемые фото и проектные материалы. Если его нет, обезличить пример и проверить, что связка географии/дат/фотографий не позволяет ненамеренно раскрыть объект.
- Документ соответствия показывать только для применимого юрлица/изделия/срока. Не превращать сертификат комплектующего в сертификат всей установки.

**Приватные вложения заявок не являются источником материалов для сайта**. Их не открывали и не предлагают использовать. Нет разрешения → нет новой публикации клиентского материала, даже если он похож на уже показанный.

## 6. Проверки владельцем и воспроизводимый протокол видимости

### Владелец в доступных кабинетах

1. **Яндекс Вебмастер:** подтвердить права на правильный HTTPS-host; проверить индексирование и выбранные канонические URL из 19, исключения/ошибки, sitemap и актуальную серверную версию после будущего внедрения. Сопоставить запросы/показы с конкретными страницами.
2. Уточнить реальные региональные сведения и карточку организации; Россия как цель бизнеса не равна существованию офисов во всех регионах.
3. **Wordstat/доступные инструменты:** проверить группы из матрицы, полноформатные названия и неоднозначные аббревиатуры. Сохранить дату/регион/тип совпадения. Не подменять показы Вебмастера полным рыночным спросом.
4. **Search Console, если доступен:** проверить sitemap/URL и обычную видимость отдельно от опыта Яндекса; сравнить запросы/посадки. Google-результаты не подтверждают Алису.
5. **Журналы сервера у владельца:** проверить фактические запросы/статусы/IP нужных роботов, их подлинность по официальной процедуре; оценить WAF/CDN и доставку текста. UA-строка или общий robots Allow не доказывают визит.
6. **Официальные материалы Яндекса:** открыть актуальные alice/epos/user-agent, зафиксировать дату и релевантные положения. Проверка специальных правил Алисы остаётся незавершённой из-за недоступности источников.
7. Аналитику/обращения изучать отдельно. Реальная заявка в backend, goal lead_success, клики, посещения, упоминание в ответе и цитата — разные события. Согласие/ошибки/дедупликация могут объяснять расхождения. Не менять текущую интеграцию в рамках аудита.

### Фиксированная панель вопросов

Использовать **B1–B6, T1–T6, W1–W6, F1–F6, A1–A6, D1–D6, M1–M6, C1–C6** из page-matrix: 48 неизменённых формулировок. Включены выбор/сравнение/ограничения/комплект/данные/производитель во всех направлениях. Не добавлять бренд в небрендовый вопрос ради получения упоминания.

Порядок после получения доступа, затем после внедрения:

1. **До внедрения** получить реальную исходную выборку из опубликованного сайта: локальная матрица не заменяет baseline поисковых ответов.
2. Сервис по умолчанию для панели: **Яндекс Поиск с ответом Алисы AI**, если режим реально доступен; самостоятельную Алису/другой ИИ вести как отдельную серию. Записать точный сервис, URL/название режима, дату/время Europe/Moscow, фактический регион поиска, язык, устройство, вход в аккаунт/персонализацию. Для сравнения использовать один согласованный регион (например, Москва); это условие эксперимента, не объявление реальной географии бизнеса. Нельзя предположить регион по часовому поясу.
3. Каждый вопрос запускать в новом независимом контексте с одинаковыми условиями, без подсказок/истории беседы. Записывать точную формулировку, полный допустимый результат/источники, видимость режима. Если AI-ответ не выдан — отдельный статус, а не «сайт исключён».
4. Для каждой записи раздельно отмечать: **упоминание ЭЭ**, **ссылку на домен**, **цитирование конкретной релевантной страницы**, **корректность сведений о компании/изделии**, **обычный результат поиска**. Проверять фактический URL, не только название в тексте.
5. Провести повторную серию в иной день; фиксировать вариативность, не выбирать только удачные ответы. Одно отсутствие не доказывает исключение, одно присутствие — устойчивую видимость.
6. После разрешённого внедрения зафиксировать дату/версию и момент обнаружения обновлённого текста инструментами владельца; повторить ту же панель в сопоставимых условиях. Интервал задавать календарно и сохранять в журнале, не обещая срок переобхода.
7. Сравнивать пары по ID вопроса, региону и режиму. Условия отличаются → отдельная серия, а не «рост/падение». Изменение ответа может иметь другие причины; причинность доработок этим наблюдением не доказана.

`run_id | date_time_tz | question_id | exact_question | service | mode | region | device | login_context | site_version | AI_answer_available | company_mentioned | domain_link | cited_page_URL | factual_errors | ordinary_search_result | evidence_reference`
