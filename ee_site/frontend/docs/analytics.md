# Метрика, согласие и источник обращения ООО «Энергоэффект»

Ветка `feature/ee-analytics`; исходный HEAD
`f611bcd0b09c078e224ad9887abc7c57234a8bfb`. Только ee_site. Это реализация для
последующей приёмки, не изменение production/аккаунта. По умолчанию сбор отключён
(`VITE_EE_ANALYTICS_ENABLED=false` или переменная отсутствует).

## Архитектура и границы

- `src/analytics/policy.js`: фиксированные маршруты/slugs/параметры, фильтрация
  рекламных кодов, сроки. `store.js`: согласие, кампании, дедупликация целей.
- `runtime.js`: единственный адаптер; UI никогда не вызывает `ym` напрямую.
  `AnalyticsBridge.jsx` читает завершённую навигацию React Router после Seo effects.
- `analytics-frame.html` / `frame.js`: отдельный невидимый документ счётчика на
  том же origin. Его собственный адрес не содержит пользовательских query, title
  или fragment (только технический числовой token в hash). У него нет DOM формы,
  `referrerpolicy=no-referrer`, meta referrer=no-referrer. Самостоятельное открытие
  файла или встраивание без same-origin handshake не загружает Метрику.
- Счётчик **113583806**, production-сборка, HTTPS, только точные hostname
  `energoeffekt-rostov.ru`, `www.energoeffekt-rostov.ru`, явный build flag `true` и
  выбор пользователя. Эти же ограничения действуют внутри iframe. На localhost,
  preview/staging, dev и при выключенном флаге нет ни скрипта, ни сохранения/
  передачи рекламного источника. Mock не является runtime-настройкой приложения:
  тестовый браузер перехватывает все URL до сети.
- После загрузки: `defer:true`, ручные `hit` и `reachGoal`, `clickmap:false`,
  `trackLinks:false`, `accurateTrackBounce:false`, `trackHash:false`,
  `webvisor:false`, `ecommerce:false`, `triggerEvent:false`, **`disableYtm:true`**.
  Не добавлены noscript, preload, Advanced Matching, firstPartyParams, setUserID,
  сторонние пиксели, Вебвизор, ecommerce, CRM или офлайн-конверсии.
- При отзыве адаптер сначала запрещает команды/меняет generation, синхронно
  вызывает `ym(id,'destruct')`, затем удаляет весь iframe. Это уничтожает его
  browsing context с обработчиками/таймерами, а не только script. Не перезагружает
  основной документ и не сбрасывает форму. Поздние ready/onload от старого token
  не принимаются; повторное разрешение создаёт новый экземпляр.
- Таймаут загрузки 10 секунд. Ошибки загрузки/блокировщик/CSP/исключения не мешают
  API или навигации. Интерактивные цели во время загрузки не ставятся в очередь. До готовности
  допустима ограниченная очередь **25 просмотров только после согласия**; она
  очищается при отзыве/таймауте. Это best effort: потерянные события не повторяются.
  Подтверждённый `lead_success` при действующем разрешении — исключение:
  до **20 UUID**, не более **10 секунд** ожидания готовности. Очередь в памяти
  очищается при отзыве, expiry согласия, таймауте и смене поколения; старые
  успехи после повторного разрешения не воспроизводятся. Без разрешения очереди нет.
  Уже начавшийся до отзыва сетевой запрос может завершиться.

## Согласие и хранение

Новый выбор явный: «Разрешить аналитику», «Без аналитики». Повторное открытие —
кнопка «Настройки аналитики» в Footer; фокус переходит на действие и возвращается
после выбора/закрытия. Панель не модальная, не блокирует страницу и доступна с
клавиатуры. Нет обещания, что продолжение просмотра означает согласие.

| Данные | Storage / состав | Срок / границы |
|---|---|---|
| Выбор | localStorage `ee_analytics_consent_v1`: `{version:1,choice:"allowed" или "denied",at:<ms>}` | 180 дней от выбора; изменяемая `CONSENT_DAYS` |
| Кампании | localStorage `ee_campaign_v1`: `{version:1,first:{tags,at},last:{tags,at}}` | 30 дней; изменяемая `ATTRIBUTION_DAYS` |
| Попытки цели успеха | localStorage `ee_goal_success_v1`: массив `{id:<submission UUID>,at}` | до 200 записей / 30 дней; UUID только внутри приложения |
| Ручной retry | sessionStorage `ee_submission_retry_v1`: версия, до 10 записей `{id,signature,at,direction,attribution,consentAt}` | 24 часа от последней ручной попытки, в пределах вкладки; необязательная часть только при разрешении |

`ee_cookie_consent=accepted` не считается согласием и не переносится. Неизвестная
версия, повреждение, недопустимый выбор или срок — выключено, требуется новый
выбор. При изменении схемы повысить `VERSION`, сменить ключи и удалить старые
необязательные данные. Не переносить согласие автоматически. Expiry контролируется
таймером и при возвращении фокуса; storage event синхронизирует вкладки.

Чтение/запись storage защищены try/catch. При отказе записи явный выбор действует
в текущем документе; reload снова безопасно выключает аналитику, если нет
сохранённого актуального разрешения. Фокус не отменяет session-only выбор из-за
старого отказа в readable storage. При недоступном sessionStorage восстановление
retry через reload невозможно; до reload ключ и поля остаются в памяти.
Если новое решение записать нельзя, приложение пытается удалить старое согласие,
включая прежнее allowed. Доступное удаление предотвращает восстановление этого
разрешения после reload и вызывает стандартный storage event в других вкладках.
Если запрещены и запись, и удаление, текущий документ остаётся без аналитики
после отказа; focus/storage events со старым allowed не отменяют этот отказ.
Однако прежнее allowed может сохраниться для reload и другой вкладки: гарантировать
сохранение отказа в таком браузере невозможно. Отдельной межвкладочной рассылки нет.
Если очистка рекламной части retry не может перезаписать sessionStorage,
приложение удаляет весь сохранённый retry, сохраняя технический UUID/направление
в памяти. Это может лишить восстановления ключа после reload. Если удаление
также запрещено, память очищается, но старую запись физически удалить нельзя;
восстановленная рекламная часть используется только при совпадении разрешения.

Отзыв удаляет first/last из памяти и storage, необязательную часть retry-снимков,
локальную историю передачи целей и доступные cookies `_ym_*` для `/` на текущем
hostname/apex, а также ключи storage с префиксом `_ym`/`__ym`. Недоступный storage,
HttpOnly cookies, иные cookie paths и сторонние домены удалить приложением нельзя.
Используйте настройки браузера и процедуры сервиса. Данные, ранее переданные
Яндексу или сохранённые в Lead, автоматически не удаляются. Технический отказ
остаётся сохранённым. Операционные данные retry сохраняются независимо от
аналитики, без значений формы/документов. Signature — хеш содержимого запроса,
а не обещание анонимизации: доступ к техническому storage должен быть защищён.

## SPA и безопасные адреса

Выбран `defer:true` + только ручной `hit`. Начальный hit после разрешения один.
Реальный другой pathname даёт один hit; Back/Forward учитываются вновь. Повторный
render/effect и StrictMode не дублируют одинаковый текущий путь. Якоря/аккордеоны/
query на том же pathname не считаются новой страницей. Нормализация `/contacts`
сохраняет существующий переход `/#contacts`, теперь сохраняя query для допустимых
рекламных меток; alias и `/` представлены одним путём. History не очищается ради
аналитики. Документы/форма не перемонтируются из-за выбора согласия.

Модальный кейс: `case_open`, без нового виртуального просмотра; возврат к фону
не создаёт hit. Прямой `/cases/<из allowlist>` — обычный hit, без case_open.
Title берётся после завершения Seo effects текущего маршрута; у модального кейса
остаётся title фоновой страницы. URL всегда имеет фиксированный origin
`https://www.energoeffekt-rostov.ru`, известный pathname и не имеет fragment.
Неизвестный маршрут/slug представлен `/404`, без исходного текста URL.

**Только первый hit данной разрешённой сессии** может включать текущие валидные
UTM/yclid. Следующие переходы используют чистый URL, чтобы не изображать новые
рекламные входы. Исходный referrer: только известный внутренний safe path либо
категория `https://yandex.ru/` / `https://www.google.com/`; остальные — пусто.
Внутренний referrer — предыдущий безопасный путь. Никакого raw referrer в Lead.

Если выбор сделан после ухода с размеченного URL, источник не восстанавливается
по предположению. Действия до разрешения/за период отказа не отправляются. Даже
если текущая страница присутствовала до выбора, учитывается только её разрешённый
просмотр. При задержке tag.js разрешённые просмотры сохраняют свои title/path;
последующие SPA просмотры не наследуют метки первого hit.

## Атрибуция и правила UTM для подрядчика

Только `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`,
`yclid`. Прочие query отбрасываются. Для UTM: 1–64 символа, первая буква a-z,
дальше только a-z/0-9/underscore/hyphen; 7 последовательных цифр запрещены.
Для yclid: только цифры, 1–32 знака. Повторяющийся или невалидный разрешённый
ключ отклоняет весь рекламный вход, вместо частичного личного источника.
Один набор tags до 1024 символов, структура first/last до 2048. Backend
самостоятельно проверяет строгую схему, ключи, типы, символы, размеры,
порядок first <= last и разумный timestamp (2000 год — now + 5 минут).
Backend expiry не отклоняет исторический retry; frontend удаляет просроченное
необязательное значение перед следующим POST.

Использовать только согласованные **коды кампаний**, например:
`utm_source=yandex&utm_medium=cpc&utm_campaign=btp_rostov&utm_content=search_a&utm_term=heating_units`.
Не вставлять свободный поисковый текст, персонализированные macros, ФИО, телефон,
email, компании/идентификаторы людей, CRM id, URLs, названия/содержимое файлов
или их хеши. Не подменять yclid контактными номерами. Алфавитная валидация сама
по себе не отличит код от имени человека, а цифровой yclid от другого номера:
контроль словаря подрядчика и настройка ссылок обязательны. Код не обещает
распознавание всех ПД внутри синтаксически допустимого значения.

First touch — **первый допустимый размеченный вход, сохранённый после разрешения**,
а не гарантированный первый визит человека. Last campaign touch — последний
допустимый размеченный вход после разрешения. Повторный effect на том же URL
не продлевает срок; новый загрузочный вход может обновить last, даже с теми же
метками. Внутренний переход без меток не стирает источник. Первый touch истекает
через 30 дней: создаётся новая история только при новом размеченном входе.
Отсутствие меток — **неизвестный источник**, не доказанный direct/organic.
Размеченный новый URL обновляет сохранённый источник, но не историю уже начатой
отправки. Cookies/clientID или полный URL/referrer для backend не добавлены.

## Lead API, snapshot и идемпотентность

Новые optional multipart поля: `direction_type` (`product`/`service`/пусто),
`direction_slug` (фиксированный список продукции/услуг), `campaign_attribution`
(JSON-строка строгой схемы). Старые клиенты работают без них. Поля write_only,
публичный ответ остаётся `{id}` / `{id,duplicate:true}`. Направление берётся из
выбранной опции существующего TopicSelect, а не из произвольного description.
Оно операционное и отправляется при любом согласии. Общая заявка без выбора
направления имеет пустые поля. Admin показывает направление, first/last и
«Неизвестный источник»; значения в admin стандартно экранируются Django.

Новая миграция `0007_lead_campaign_attribution_lead_direction_slug_and_more`
добавляет JSONField default={} и два blank CharField. Исторические миграции,
приватные вложения, endpoint protections и notification queue не изменены.

**Совместимое правило:** fingerprint/hash и набор прежних содержательных полей/
документов не меняются. Новые служебные поля не включены в hash; для них действует
**первое принятое значение**, включая направление. При retry другая кампания,
expiry, отзыв или отсутствие metadata не вызывает 409, не меняет существующий
источник и не создаёт документы/уведомления. Изменённые имя/телефон/description/
source_page/source_system/файлы по-прежнему вызывают 409 для того же UUID. Выбор
другой темы по-прежнему меняет штатный description и клиентский signature.
Поля metadata валидируются и в повторе: синтаксически испорченные данные дадут
400, а не silently accepted metadata. Это не отключение endpoint validation.

Перед первым запросом фиксируются направление/атрибуция; при повторе используются
тот же UUID и снимок, даже при новой кампании. Revoke очищает снимок, generation
блокирует цель старого запроса; разрешение вновь не восстанавливает старый снимок.
Ничего не удаляется из уже начавшегося POST/созданного Lead автоматически.
После ручного reload форма/документы не восстанавливаются из storage; посетитель
может заполнить её заново. При совпадении signature в течение 24 часов вкладка
восстанавливает прежний UUID/направление и разрешённый снимок с тем же consentAt;
при смене согласия отправляет без кампании. Нет автоматического POST.
Изменённое содержимое — новая попытка и новый UUID. После подтверждённого успеха
retry record удаляется: намеренная новая заявка учитывается отдельно. При 409
ключ сбрасывается как прежде. При закрытии вкладки/expiry/отказе sessionStorage
такое восстановление не гарантируется; ключ не передаётся в Метрику.

`lead_success` дедуплицируется по UUID на уровне памяти и доступного localStorage:
после подтверждённого 201/200 один вызов, до 30 дней/200 записей. Потерянный 201,
затем ожидаемый 200 — первый подтверждённый успех. Новая заявка — отдельный UUID.
Отказ/другая generation/старый consentAt не допускают отправку после нового выбора.
Состояния различаются: **ожидание** готовности не записывает UUID как переданный;
**локальная передача** означает, что postMessage в готовый iframe завершился
без исключения. Только после этого UUID отмечается в dedup-хранилище.
Это не ACK приёма iframe и не **доставка в Яндекс**: подтверждения сервиса нет.
При исключении postMessage ложная отметка не создаётся; повторный вызов success
может повторить локальную попытку без повторения POST заявки. Автоматических
повторов или обещания exactly-once. Одновременная race между вкладками может
дублировать цель: localStorage read/write не транзакция. Недоступное storage
ограничивает дедуп одним документом; revoke очищает историю передачи. Backend
идемпотентность остаётся источником истины о заявках, а не аналитический счётчик.

## Production, CSP и отключение

Никаких deploy/migrate/merge/push/PR этой работой не выполняется. Для последующего
внедрения сначала согласовать тексты, кабинет и приёмку; применить новую миграцию
к согласованной БД, затем собрать с `VITE_EE_ANALYTICS_ENABLED=true`. Настройка
вшивается Vite при build: изменение окружения без пересборки её не меняет.
Выключение: пересобрать с `false` и развернуть в отдельной согласованной операции.
После reload выключенная сборка удаляет доступные optional data и не создаёт
iframe. Уже открытые документы старой сборки не получают новый флаг автоматически:
для аварийного прекращения в них использовать отзыв или согласованную серверную
блокировку аналитических destinations. Не обещать мгновенный kill switch для
уже загруженных вкладок.

CSP — рекомендации, **не изменение текущего nginx**. Для выбранной минимальной
конфигурации рассмотреть точные добавления к существующей политике:

```text
script-src: https://mc.yandex.ru
connect-src: https://mc.yandex.ru https://mc.yandex.com
img-src: https://mc.yandex.ru https://mc.yandex.com
frame-src: 'self'
```

Сохранить действующие разрешения для локальных bundles/assets/API. Для
`analytics-frame.html` разрешить `frame-ancestors 'self'`, если текущая политика
запрещает все iframe. Это не необходимость открыть сайт для любых чужих origin.
Наш код — внешний module, nonce/unsafe-inline/unsafe-eval ему не нужны. Для уже
существующих inline JSON-LD сохранить/проверить действующее правило отдельно.
`noscript` не добавлять. В локальном перехвате tag.js v2660 фактически выбрал
`mc.yandex.com` для watch/advert.gif; поэтому этот точный hostname указан наряду
с `.ru`, а не только предполагается по адресу скрипта. Официальная CSP-справка перечисляет также региональные
mc.yandex.* destinations и yastatic.net: не добавлять их все автоматически.
Проверить библиотеку/CSP Report-Only на согласованной среде; добавить только
фактически нужные **точные** hosts из официального списка. При заблокированном
нужном endpoint аналитика может потеряться, но форма продолжает работать.

### Что владелец проверяет перед публикацией

1. Назначение обработки/правовые основания, формулировки согласия и раздела 6
   текущей политики, применимые обязанности по cookies/аналитическим данным.
2. Участников/условия передачи в Яндекс, IP/идентификаторы/cookies, реальные
   сроки в кабинете, действительность выбранных 180/30 дней, процедуры обращений.
3. Разделы 9–11 текущей политики, фактическую территорию обработки и вопрос
   трансграничной передачи. Их существующие общие формулировки не подтверждены
   технической реализацией и не являются гарантией соответствия закону.
4. Как обрабатывается запрос на удаление ранее переданных данных/сохранённых
   заявок; отзыв в UI автоматически их не удаляет. Реквизиты не выдумывались.
5. Настройки счётчика/отключённые auto goals, Advanced Matching, YTM и лишние
   интеграции; фактические payload tag.js, его чтение top/parent и сетевое поведение
   после destruct; CSP, cookies и поступление разрешённых целей после публикации.
6. Рекламные коды подрядчика: синтаксис не обеспечивает отсутствие ПД по смыслу.

## Автоматические проверки и ручная приёмка

Из frontend: `npm test`, `npm run lint`, `npm run build`.
Из backend с установленным venv:

```sh
python manage.py test --settings=config.settings.test --noinput
python manage.py check --settings=config.settings.test
python manage.py makemigrations --check --dry-run --settings=config.settings.test
```

Браузер: отдельная SQLite DB, `config.settings.test` с локальным file DB,
`ALLOWED_HOSTS` localhost, background queue, private uploads вне checkout; только
loopback API. Тестовый браузер перехватывает **все** внешние запросы и файлы
production-сборки по виртуальному HTTPS production hostname без обращения к
production. CA/TLS не меняются. Зависимость Playwright устанавливается отдельно;
никакой тестовый флаг приложения или путь к реальному трекингу не добавлен.

```sh
VITE_EE_ANALYTICS_ENABLED=true npm run build
PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs CHROME_PATH=/usr/bin/chromium \
ANALYTICS_TEST_API=http://127.0.0.1:8011 ANALYTICS_OUTPUT=/tmp/ee-analytics-browser \
node scripts/analytics-browser.mjs
```

Настоящий tag.js: обычным TLS-проверяемым GET получить официальный
`https://mc.yandex.ru/metrika/tag.js` в локальный файл; добавить
`METRICA_TAG_FILE=/absolute/path/tag.js` к **той же** команде. Все запросы
библиотеки перехватываются/подменяются до доставки. Без файла результат явно
`UNVERIFIED`, а не успешная проверка настоящей библиотеки. При обнаружении
передачи пользовательского URL/top/parent/ПД не включать интеграцию, исправить
и повторить этот этап. Получение данных в настоящем кабинете — отдельная
приёмка после публикации, не часть данного теста.

Windows/Chrome, локальная/согласованная тестовая среда:

1. Открыть DevTools Network/Storage, очистить только test data. До выбора нет
   tag.js/watch; старое accepted не скрывает новый выбор.
2. Выбрать отказ: форма/контакты/документы работают. Reload сохраняет отказ.
   Открыть настройки Tab/Enter; разрешить, проверить один init/первый hit.
3. BTP → другая услуга → Back/Forward: по одному hit с правильным title;
   якорь/FAQ без hit; contacts один `/`; модальный case только case_open,
   прямой case — hit. Проверять все network payload, не только консоль ym.
4. Заполнить поля/два файла. Отозвать, проверить destruct, прекращение новых
   запросов и сохранность полей/документов; повторно разрешить — нет backlog.
   Повторить во второй вкладке, при медленной/заблокированной загрузке скрипта.
5. Изолированный API: потеря первого ответа → ручной retry 200, один Lead/набор
   файлов/job и первая цель; 201 → повтор того же UUID 200 без второй цели;
   новая заявка отдельно. 400/409/413/429/500/HTML/network — без цели, поля целы.
6. Новый рекламный вход, expiry/reload/revoke → неизменённая retry-заявка без
   неожиданного 409 или перезаписи источника. Отказ storage безопасен.
7. 360/390/1440px, клавиатура: banner без horizontal overflow; фокус доступен;
   отказаться можно столь же явно. Адрес браузера не чистится ради аналитики.
8. Только после отдельной публикации проверить появление разрешённого hit/
   lead_success в кабинете. Не суммировать клики/auto goals с заявками.

Сравнение начальной загрузки (`analytics-load.mjs`) с отдельно собранным
исходным HEAD, без сетевых запросов в production:

```sh
PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs CHROME_PATH=/usr/bin/chromium \
ANALYTICS_BASELINE_DIST=/absolute/path/to/baseline/dist \
ANALYTICS_LOAD_OUTPUT=/tmp/ee-analytics-load.json node scripts/analytics-load.mjs
```

Результаты конкретного запуска и влияние на начальную загрузку записываются
в `docs/analytics-validation.md`; mock стоимость не означает стоимость tag.js.
