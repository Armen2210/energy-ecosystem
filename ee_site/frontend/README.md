# Frontend сайта «Энергоэффект»

Этот каталог содержит клиентскую часть сайта ООО «Энергоэффект»: публичное SPA-приложение с каталогом продукции и услуг, кейсами, контактным блоком, формой заявки и страницей политики обработки персональных данных.

Документ описывает состояние исходного кода в репозитории. Он не подтверждает состояние production, сервера, DNS, почты, базы данных или внешних кабинетов: это нельзя установить по frontend-коду.

**Дата основного описания:** 29 сентября 2026 года; актуализация по коду — 10 октября 2026 года. Аналитика добавлена 9 октября 2026 года; подробности и границы — в [analytics.md](docs/analytics.md), результаты — в [analytics-validation.md](docs/analytics-validation.md).

## Продуктовый контекст

Это сайт производственной компании ООО «Энергоэффект», ориентированный на B2B-аудиторию.

- продукты: БМК, БТП, ВНС, ПНС и ШУиА;
- услуги: проектирование, СМР и ПНР;
- цели frontend: представить компетенции компании, сформировать доверие к ней и получить заявку от потенциального заказчика;
- текущий объём frontend — production-ready MVP;
- CMS, личный кабинет, конфигуратор, калькуляторы и платформенные функции в текущий frontend не входят.

## Эксплуатационный контекст

В этом разделе сведения владельца проекта намеренно отделены от фактов, установленных по frontend-коду.

**Сведения владельца проекта:**

- production-домен — `https://www.energoeffekt-rostov.ru`;
- frontend работает совместно с backend на Django и Django REST Framework;
- production использует SPA fallback для прямого открытия внутренних маршрутов;
- состояние production проверяется отдельно от локальной сборки.

**Факты, подтверждённые frontend-кодом и структурой репозитория:**

- заявки отправляются через backend endpoint `/api/leads/`;
- URL запроса составляется из `VITE_API_BASE_URL` и `/api/leads/`;
- клиент использует `BrowserRouter`, поэтому прямое открытие внутренних маршрутов требует SPA fallback в среде размещения; конфигурация production-сервера в frontend-каталоге отсутствует.

## Быстрый старт

Требуется среда Node.js с npm. Конкретная версия Node.js в репозитории не зафиксирована (`.nvmrc` и поле `engines` отсутствуют).

```bash
cd ee_site/frontend
npm ci
cp .env.example .env
npm run dev
```

В `.env.example` объявлены frontend-переменные:

```text
VITE_API_BASE_URL
VITE_EE_ANALYTICS_ENABLED=false
```

`VITE_API_BASE_URL` задаёт базовый URL backend без завершающего `/api/leads/`. `VITE_EE_ANALYTICS_ENABLED=true` явно включает возможность аналитики в production-сборке, после согласия и только на разрешённых HTTPS-hostname; по умолчанию выключено. Значение для конкретной среды необходимо задавать локально; секреты и реальные реквизиты окружения в README не приводятся. Vite автоматически загружает `.env`, а корневой `.gitignore` исключает его из Git.

Для Windows/PowerShell вместо `cp` используйте `Copy-Item .env.example .env`.
`npm ci` использует существующий lockfile; `npm install` нужен при намеренном
обновлении зависимостей. Backend запускается отдельно по [его README](../backend/README.md).

### Приоритет переменных Vite

От высокого приоритета к низкому: переменные процесса → `.env.[mode].local` →
`.env.[mode]` → `.env.local` → `.env`. Файлы с mode дополняют и переопределяют
общие. Dev использует mode `development`, build — `production`; `--mode` меняет
mode, но не превращает dev server в production-сборку. `.env.example` автоматически
не загружается. После изменения файлов перезапустите dev server или пересоберите
bundle. Все `VITE_*` значения попадают в публичный frontend, секретов там быть не должно.

### Scripts из `package.json`

| Команда | Назначение |
| --- | --- |
| `npm run dev` | Запускает Vite dev server. |
| `npm run build` | Создаёт production-сборку в `dist/`. |
| `npm run preview` | Локально раздаёт ранее созданную production-сборку Vite. Сначала нужен `npm run build`. |
| `npm run lint` | Запускает ESLint для проекта; каталог `dist` исключён конфигурацией. |
| `npm test` | Node test runner: `src/api/*.test.js` и `src/analytics/*.test.js`. |

`npm test` запускает Node-тесты API и аналитики. Отдельных scripts для форматирования или type-check нет.

## Архитектура приложения

`index.html` содержит `#root`; `src/main.jsx` подключает шрифты, `src/index.css`, включает React `StrictMode`, создаёт root и оборачивает `App` в `BrowserRouter`.

`src/App.jsx` формирует общий каркас:

1. `Header`;
2. `ScrollToTop`, управляющий прокруткой при маршрутах, hash-переходах, переходах к форме и возврате из кейса;
3. основной `Routes`;
4. дополнительный `Routes` для `CaseModal`, когда в `location.state` есть `backgroundLocation`;
5. `Footer`;
6. `CookieBanner`.

`AnalyticsBridge` связывает SPA-навигацию и разрешённые действия с адаптером аналитики. В `main.jsx` также нормализуется начальный `/contacts` до `/#contacts` с сохранением query.

Приложение полностью клиентское. Для прямого открытия внутренних URL сервер, который раздаёт сборку, должен возвращать `index.html` для неизвестных файловых путей. Конкретная серверная конфигурация в этом frontend-каталоге не задаётся.

Контент каталога не запрашивается с API: продукты, услуги, кейсы и главное меню импортируются из `src/data`. Backend вызывается только при отправке формы заявки.

## Страницы продуктов и услуг

`ProductPage` и `ServicePage` получают `slug` из URL, находят сущность в соответствующем data-массиве и собирают страницу из общего набора элементов:

- `PageNavigation` с возвратом к соответствующей секции главной и хлебными крошками;
- `EntitySwitcher` для перехода только между сущностями того же типа;
- hero с изображением и режимом отображения из данных;
- `AiSummary`;
- `ProductDetailsAccordion`;
- списки характеристик/областей применения;
- `FAQ`, который также выводит JSON-LD `FAQPage`;
- секция `#lead-form` с `LeadForm` и заранее выбранной текущей темой.

FAQ для этих страниц определён в самих `ProductPage.jsx` и `ServicePage.jsx`, а не в data-файлах. `EntitySwitcher` вычисляет высоту sticky-header и передаёт направление перехода через `location.state`. На desktop переключатель расположен вертикальной sticky-рейкой слева от контента; на tablet/mobile сохраняется горизонтальная sticky-лента с прокруткой активного пункта в видимую область.

## Основные компоненты

- `Header` — логотип, знак «12 лет», desktop/mobile-навигация, активный пункт и переходы к секциям.
- `Footer` — навигация, контакты, юридические данные, ссылка на политику и внешние ссылки экосистемы. На desktop используется симметричная трёхколоночная раскладка; tablet/mobile сохраняют отдельную responsive-компоновку.
- `PageNavigation` — общий блок возврата и хлебных крошек для внутренних страниц; используется на страницах продуктов, услуг, объектов, «О компании» и политики.
- `Hero` — главный экран главной страницы.
- `SectionHeader` — унифицированный заголовок секции.
- `ProductCard`, `ServiceCard` — карточки, ведущие на детальные страницы.
- `AiSummary` — компактное структурированное резюме сущности или страницы.
- `EntitySwitcher` — sticky-переключатель продуктов/услуг.
- `ProductDetailsAccordion` — аккордеон детального контента; первый элемент открыт по умолчанию.
- `FAQ` — раскрывающиеся вопросы и JSON-LD `FAQPage`.
- `InfoListBlock`, `TrustBlock` — типовые содержательные списки/карточки.
- `LeadForm` — сбор и отправка заявки.
- `CaseCard` — карточка объекта и вход в modal/direct сценарий. На desktop главной используется фотогалерейный вариант `.cases-grid--home` с hover-обрамлением; на внутреннем реестре — отдельный модификатор `.cases-grid--page`.
- `CaseModal` — доступная модальная оболочка кейса: backdrop, Escape, focus trap, блокировка фонового scroll и возврат к источнику.
- `CaseView` — общее содержимое кейса, галерея, клавиатурные стрелки, свайп, метаданные и CTA.
- `Seo` — обновление title, description, Open Graph URL/title/description и canonical при клиентской навигации.
- `ScrollToTop` — специальная логика позиционирования для маршрутов, якорей и возврата из объектов. Для возврата с внутренних страниц используются прямые сценарии `cases-direct`, `products-direct`, `services-direct` и `contacts-direct`, которые сразу позиционируют главную на нужной секции без видимого скролла от Hero.
- `CookieBanner` — единый компактный блок «Помогите нам стать удобнее», кнопки «Разрешить аналитику» / «Без аналитики», раскрытие «Подробнее». Повторное открытие — кнопкой «Настройки cookies» над ссылкой на политику в Footer; текущее решение относится именно к аналитике, «Закрыть» его не меняет. Согласие формы отдельно. Старое `ee_cookie_consent=accepted` не даёт разрешения. На ширине от 1000 px действия справа, на меньших — под текстом; низкий экран допускает прокрутку и keyboard focus.

`ProcessSteps` и `ContactsPage` присутствуют в исходниках, но текущим деревом маршрутов/страниц не используются. Это важно учитывать перед удалением или изменением «неиспользуемого» кода.

## Источники данных

### `src/data/products.js`

Массив из пяти продуктов. Он используется на главной, в `/solutions`, на `ProductPage`, в `EntitySwitcher` и в вариантах выбора `LeadForm`. Объекты содержат идентификаторы и URL, полные и сокращённые названия, карточный и hero-контент, изображение и режим изображения, опциональный логотип линейки, цветовую тему, AI Summary, подробные секции, характеристики и области применения.

ПНС в проекте означает пожарные насосные станции.

### `src/data/services.js`

Массив из трёх услуг: проектирование, строительно-монтажные работы и пусконаладочные работы. Используется на главной, в `/services`, на `ServicePage`, в переключателе и форме. Контракт близок к продуктам: slug/URL, названия, карточный и hero-контент, изображение, тема, AI Summary, подробные секции, характеристики и варианты применения.

### `src/data/cases.js`

Массив из пяти кейсов и производный экспорт `featuredCases = cases.filter(isFeatured)`. Все пять объектов имеют `hasDetailPage: true`; три помечены `isFeatured: true`. В пользовательском интерфейсе используется термин «Объекты», при этом технические имена `cases`, slug и route `/cases` сохранены.

Объект кейса хранит slug, URL, тип/категорию, заголовки и описания, cover, галерею с `image`/`alt`/`caption`, SEO, местоположение, год, тип и длительность проекта, задачу, поставленные системы, выполненные работы, особенности решения, AI Summary, CTA и связи с продуктом/услугами. Фотографии импортируются из `src/assets/cases/<slug-каталог>/`.

### `src/data/navigation.js`

Четыре пункта главного меню: продукция, услуги, объекты и контакты. Все ведут к hash-секциям главной; для объектов технически используется `/#cases`.

При изменении slug или URL необходимо согласованно проверить data-объект, ссылки, маршруты, `sitemap.xml`, SEO path и каталоги изображений.

## Кейсы: modal и прямой просмотр

`CaseCard` всегда содержит обычную ссылку на `caseItem.url`, поэтому стандартное открытие в новой вкладке сохраняется. Обычный левый клик перехватывается и выполняет `navigate` с двумя объектами состояния:

- `backgroundLocation` — страница, которая остаётся под модальным окном;
- `modalOrigin` — pathname/search, scroll-позиция и slug карточки для возврата.

При наличии `backgroundLocation` основной `Routes` продолжает отображать исходную страницу, а второй набор маршрутов в `App.jsx` показывает `CaseModal` по тому же `/cases/:slug`. Закрытие кнопкой, кликом по backdrop или Escape возвращает к исходному pathname и передаёт `caseReturn`; `ScrollToTop` восстанавливает позицию/карточку.

Если пользователь напрямую открывает `/cases/:slug`, `backgroundLocation` отсутствует и отображается `CasePage`. Она добавляет SEO, хлебную крошку, ссылки на реестр и тот же `CaseView`. Поэтому содержимое и галерея едины для modal и прямой страницы, а оболочка, SEO и навигация различаются.

`CaseView` циклически переключает изображения кнопками и стрелками клавиатуры, распознаёт горизонтальный touch-свайп от 50 px, предзагружает соседние изображения и сбрасывает активный индекс при смене кейса.

## LeadForm и backend API

Форма используется на главной и на детальных страницах продуктов/услуг. Существующий, но не подключённый `ContactsPage` также содержит форму.

### Поля формы

| Поле | HTML name | Особенности |
| --- | --- | --- |
| Имя | `name` | Обязательное. |
| Компания | `company_name` | Необязательное. |
| Телефон | `phone` | Обязательное. |

| Описание | `description` | Необязательное textarea. |
| Источник | `source_system` | Скрытое фиксированное значение `ee_site`. |
| Страница | `source_page` | Скрытое значение из текущих `window.location.pathname` и `hash`. |
| Согласие | `consent` | Проверяется обработчиком перед отправкой, но не отправляется в API. |

При submit создаётся `FormData`. Если направление выбрано, оно объединяется с пользовательским описанием в поле `description`; временные поля `description_topic` и `consent` удаляются. Кнопка и fieldset блокируются на время запроса. После подтверждённого успеха форма и выбранные файлы сбрасываются, сообщение скрывается через таймер; при ошибке поля и документы сохраняются, отображается понятное сообщение. Автоматических повторных POST нет. Для 429 учитывается `Retry-After`, для 413 предлагается уменьшить документы; JSON field errors/detail, HTML и сетевые ошибки обрабатываются отдельно.

Для одной логической отправки форма добавляет `submission_id` (UUID). Ключ
повторно используется после сетевого или неопределённого результата, пока
содержимое полей и документов не изменилось. Техническая запись retry в
sessionStorage позволяет восстановить его в пределах вкладки до 24 часов при
ручном повторном заполнении после reload; поля и файлы не сохраняются. Изменение данных создаёт новый UUID, подтверждённый успех очищает
ключ. При недоступном sessionStorage retry через reload не гарантируется.
Ответ `201` считается успехом только при наличии положительного целого `id` или допустимой числовой строки, а `200` — только для
подтверждённого повтора с `id` и `duplicate: true`. Пустой, HTML или повреждённый
успешный ответ считается неопределённым и оставляет возможность безопасного
повтора. `409 submission_conflict` требует новой логической отправки.

`src/api/leadsApi.js` выполняет:

```text
POST ${VITE_API_BASE_URL}/api/leads/
```

Тело — `FormData`, поэтому код намеренно не задаёт `Content-Type`: boundary формирует браузер. При неуспешном HTTP-статусе клиент пытается прочитать JSON, использует `detail` либо объединяет field errors. При успехе ожидается JSON-ответ.

Репозиторий подтверждает соответствующую backend-точку `api/leads/` в Django и serializer с полями формы. Frontend не содержит логики хранения заявки, email-уведомлений или администрирования; это ответственность backend, и работоспособность этих процессов требует отдельной интеграционной проверки. Завершающие `/` у `VITE_API_BASE_URL` удаляются; пустое значение использует same-origin путь `/api/leads/`.

## CSS-архитектура

Рефакторинг разнёс правила по базовым, компонентным и страничным файлам. `src/App.css` — **import-only агрегатор**: в нём нельзя размещать селекторы или временные overrides. Он подключается один раз из `App.jsx`; порядок imports участвует в каскаде и должен сохраняться осознанно.

Текущий порядок слоёв в `App.css`:

1. `styles/variables.css` — цвета и размеры дизайн-системы;
2. `styles/global.css` — reset-подобные правила, шрифты, базовая типографика, focus/touch и глобальные элементы;
3. `styles/layout.css` — `.site`, `.container`, `.section`;
4. `styles/grids.css` — сетки продуктов, услуг и кейсов;
5. `styles/cases.css` — общие actions/link реестров кейсов;
6. `styles/buttons.css` — общие `.button` variants;
7. CSS компонентов в порядке `AiSummary` → `FAQ` → `ProductDetailsAccordion` → `CookieBanner` → `TrustBlock` → `InfoListBlock` → `EntitySwitcher` → `LeadForm` → карточки → общие элементы → кейсы;
8. page-level CSS в порядке `NotFoundPage` → `PrivacyPage` → `EntityPage` → `HomePage` → `CasesPage` → `CasePage`.

`src/index.css` остаётся точкой импорта Vite/React, но сейчас содержит только комментарий. Стили компонента следует менять в его `<Component>.css`, общие токены — в `variables.css`, общую компоновку — в соответствующем файле `styles`, а общие product/service-страницы — в `EntityPage.css`.

### Responsive

Основные границы:

- desktop: шире `960px`;
- tablet/узкий layout: `max-width: 960px`;

На desktop используются многоколоночные сетки и расширенная компоновка. ## Подтверждённые ограничения и технический долг

- Неверный непустой `VITE_API_BASE_URL` направит заявку на ошибочный backend; пустое значение намеренно использует same-origin API.
- `ContactsPage` существует, но `/contacts` всегда перенаправляется на главную; компонент не импортирован в `App.jsx`.
- `ProcessSteps` экспортируется, но не используется страницами.
- В `src/assets` остаются неиспользуемые шаблонные/альтернативные файлы (`react.svg`, `vite.svg`, `hero1.jpg`); README не предлагает удалять их без отдельной проверки назначения.
- В `grids.css` есть несколько последовательных определений `.product-grid` и `.services-grid`; итог зависит от каскада. При правках нельзя оценивать только первый блок правил.
- Комментарии в отдельных JSX могут описывать прежний план (например, старый комментарий `CasesPage` про отсутствие детальных страниц), тогда как маршруты и компоненты уже реализованы. Источником истины является исполняемый код.
- Есть Node-тесты API/аналитики и отдельные браузерные сценарии; они не заменяют ручную приёмку routing, scroll, modal, responsive и submit на целевой среде.
- Корректность прямых SPA URL зависит от fallback на стороне сервера, не заданного в этом каталоге.
- Последний сохранённый результат `npm run lint` — exit 0, без ошибок/предупреждений. Старый baseline 5 ошибок / 2 предупреждения устранён предыдущими изменениями; новые задачи должны сохранять успешный lint.

## Правила безопасного внесения изменений

1. Не переносить неподтверждённые сведения о production из старых документов; отделять свойства кода от результатов внешнего smoke-test.
2. Не коммитить `.env`, токены, пароли, ключи и реальные серверные реквизиты. Публичное значение, попавшее в Vite bundle, в любом случае не является секретом.
3. Не менять slug/URL изолированно: проверить data, Router, ссылки, SEO path, sitemap и assets.
4. Сохранять разделение продуктов и услуг; формы получают оба массива, а switcher — только массив текущего типа.
5. Не дублировать данные карточек и страниц в JSX, если они уже принадлежат `src/data`.
6. Сохранять обычный link semantics в `CaseCard`, modal state и direct-page fallback.
7. Держать `CaseView` общим для modal и прямой страницы; modal-specific поведение оставлять в `CaseModal`, SEO/direct navigation — в `CasePage`.
8. Не добавлять стили непосредственно в `App.css`; учитывать точный порядок imports и специфичность каскада.
9. Проверять keyboard focus, Escape, стрелки галереи, touch-свайп и `prefers-reduced-motion` при изменении интерактивных компонентов.
10. Не задавать вручную multipart `Content-Type` при отправке `FormData`.
11. При изменении формы согласовывать HTML names с backend serializer и отдельно проверять success/error ответы.
12. Не заявлять о работоспособности production, сохранении в БД или отправке email без фактической интеграционной проверки.

## Связь с backend

Форма поддерживает до 10 документов, до 10 МиБ каждый и до 25 МиБ суммарно.
Эти значения продублированы в `src/api/leadFiles.js` для ранней браузерной
валидации. При изменении серверных `LEAD_MAX_FILES`, `LEAD_MAX_FILE_SIZE` или
`LEAD_MAX_TOTAL_FILE_SIZE` frontend-лимиты необходимо обновить одновременно.
Окончательное решение о допустимости запроса всегда принимает backend.

Frontend и backend связаны узко: форма вызывает Django endpoint `POST /api/leads/` относительно `VITE_API_BASE_URL`. В репозитории backend-маршрут подключён через `backend/config/urls.py` и `backend/apps/leads/urls.py`, а ожидаемые поля описаны serializer/model приложения `leads`.

Никакие другие frontend-страницы не получают данные с backend. Способ production-развёртывания, reverse proxy, домены, база данных, почта и фоновые процессы не определяются frontend-кодом и должны документироваться и проверяться отдельно.


## Необязательная аналитика, атрибуция и границы проверки

Счётчик **113583806** выключен по умолчанию (`VITE_EE_ANALYTICS_ENABLED=false`).
Подключение требует одновременно production-сборки, значения флага `true`, HTTPS,
точного hostname `energoeffekt-rostov.ru` либо `www.energoeffekt-rostov.ru` и
действующего явного разрешения. На localhost, dev/staging-hostname и до разрешения
библиотека не загружается. Build-флаг задаётся при сборке, не в runtime сервера.

Решение хранится версионированно до 180 дней. Отказ/отзыв запрещают новые команды,
очищают optional attribution и очередь успехов, останавливают/удаляют iframe;
поздние callbacks старого поколения отвергаются. Повторное разрешение не
воспроизводит старые события. Поля формы и выбранные документы остаются в памяти
формы при изменении решения; reload саму форму/документы не восстанавливает.
Техническое хранение выбора и retry не выключается отказом от аналитики.
При ошибке записи решения приложение пытается удалить старое разрешение.
Если запрещены и запись, и удаление, текущий документ соблюдает отказ, но его
сохранение после reload не гарантируется. Неудачная безопасная перезапись retry
может потребовать удаления всей сохранённой записи, сохраняя технический ключ
только в памяти. Детальные сроки и ограничения — в [analytics.md](docs/analytics.md).

| Событие | Что означает |
| --- | --- |
| `lead_success` | API подтвердил сохранение заявки 201 либо идемпотентный повтор 200. |
| `contact_phone_click` | Клик по tel-ссылке; не подтверждённый звонок. |
| `contact_email_click` | Клик по mailto-ссылке; не отправленное письмо. |
| `lead_form_start` | Первое действие заполнения формы; не заявка. |
| `document_selected` | Успешное добавление допустимых документов; не их отправка. |
| `calculation_cta_click` | Переход от CTA Hero/объекта к обращению; не расчёт и не заявка. |
| `case_open` | Открытие объекта в modal; прямой URL учитывается page hit. |

Параметры событий проходят allowlist. Контакты, текст заявки, файлы, UUID и ID
заявки в цели не передаются. Контактные и промежуточные действия нельзя суммировать
с заявками. Library init отключает Webvisor, автоматические клики/ссылки,
ecommerce и YTM; кабинет и внешние интеграции требуют отдельной проверки владельца.

Подтверждённый успех при разрешении может ждать готовности в памяти до 10 секунд,
максимум 20 UUID; очередь очищается при отзыве, expiry, таймауте и смене поколения.
Отметка дедуп создаётся после `postMessage` в готовый iframe без исключения,
**не после подтверждения доставки в Яндекс**. Dedup ограничен 200 UUID/30 днями,
не атомарен между вкладками. Ошибки аналитики не меняют успешный результат формы
и не вызывают повторный POST. Уже начатый сетевой запрос может завершиться после отзыва.

При разрешении сохраняются first/last marked touch до 30 дней: `utm_source`,
`utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `yclid` только по строгим
правилам кодов. В API передаётся JSON `campaign_attribution` со снимком этих входов.
Технический повтор использует исходный snapshot, без подмены источника текущим URL;
отзыв/expiry удаляют optional часть. Синтаксическая фильтрация не доказывает отсутствие
персональных данных по смыслу: подрядчик должен использовать контролируемые коды.
`direction_type` (`product`/`service`) и `direction_slug` — отдельное операционное
направление из фиксированного каталога, оно передаётся независимо от аналитического
разрешения. На backend источник и направление используют первое принятое значение
и не меняют fingerprint повторной заявки. CRM/1С-интеграции не реализованы.
