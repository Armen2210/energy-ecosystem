# Защита публичного создания заявок ЭЭ

Область: только `POST /api/leads/` в **ee_site**. Admin, скачивание приватных
документов, остальные API, GET/OPTIONS и сайт ТД не используют этот лимитер.
Форма, приватное storage, fingerprint, `submission_id` и существующая очередь
уведомлений сохранены. Схема application DB не меняется.

## Частота и гарантии

По умолчанию один IP может получить допуск к **20 попыткам за скользящие 60 секунд**
и **100 за скользящие 3600 секунд**. Лимиты считаются одновременно. Это запас для
нескольких сотрудников за общим офисным IP и ручных повторов посетителя; форма
обычно отправляет одну заявку. Учитываются также невалидные попытки, слишком
большие тела и идемпотентные повторы: иначе через них можно тратить ресурсы без
лимита. Уже отклонённые 429 не продлевают окно. После ограничения повтор с прежним
`submission_id` возвращает сохранённую заявку, не создаёт документы и уведомления.

Проверка в `APIView.initial()` выполняется до `request.data/FILES`, multipart
parsing, fingerprint и сохранения. В SQLite-файле вне application DB хранится
хеш нормализованного IP и ограниченный журнал времён допущенных попыток. Хеш не
анонимизирует IP криптографически: доступ к файлу должен быть закрыт. Просроченные
записи лимитера удаляются при следующем обращении; исторические заявки и документы
никогда не удаляются этой защитой.

`BEGIN IMMEDIATE` охватывает чтение обоих окон, проверку и запись новой попытки.
SQLite блокирует конкурирующих писателей, поэтому все Gunicorn workers **одного
хоста, использующие один и тот же локальный файл**, имеют общий атомарный лимит.
Это не LocMemCache и не неатомарный DRF throttle. Соединения закрываются после
каждой проверки. Ошибка файла, повреждение или таймаут блокировки (1 секунда)
закрывают приём с `503 / lead_protection_unavailable`, а не пропускают запрос.

Не используйте NFS, разные копии файла или разные пути по workers. Файл/каталог
должен переживать рестарт workers, быть доступен для записи web user и не раздаваться
nginx. SQLite — сериализованный локальный писатель, подходящий для умеренного
трафика публичной B2B-формы; это не распределённый лимитер. Часы хоста должны быть
синхронизированы: изменение системного времени влияет на окна и ожидание. Удаление
файла сбрасывает историю; не включайте его в периодический cleanup. При нескольких
хостах нужен согласованный edge-лимит или отдельное общее атомарное хранилище;
такой инфраструктуры это изменение не добавляет.

IP-лимит не останавливает ботнет/смену IPv6-адресов и не задаёт общий лимит диска
или размера очереди. Даже 100 разрешённых загрузок по 25 МиБ — до 2,5 ГиБ в час
на IP. Нужен мониторинг диска, nginx temp и очереди; политика хранения и orphan
cleanup находятся вне этого этапа.

## Настройки приложения

Значения читаются из окружения при запуске процесса; после изменения перезапустите
web workers. Положительные числа валидируются при загрузке настроек.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `LEAD_RATE_LIMIT_ENABLED` | `true` | `false` отключает только app IP-лимитер, не upload guards/nginx |
| `LEAD_RATE_STORE` | `<backend>/lead_rate_limits.sqlite3` | Один локальный SQLite-файл для всех web workers |
| `LEAD_RATE_BURST_LIMIT` | `20` | Число попыток в коротком окне |
| `LEAD_RATE_BURST_SECONDS` | `60` | Длина короткого окна |
| `LEAD_RATE_SUSTAINED_LIMIT` | `100` | Число попыток в длинном окне |
| `LEAD_RATE_SUSTAINED_SECONDS` | `3600` | Длина длинного окна |
| `LEAD_TRUSTED_PROXY_NETWORKS` | пусто | CIDR доверенных TCP nginx peers через запятую |
| `LEAD_TRUST_UNIX_SOCKET_PROXY` | `false` | Доверять X-Real-IP при пустом IP peer **только для защищённого Unix socket** |
| `LEAD_MAX_REQUEST_SIZE` | `28311552` (27 МиБ) | Всё тело HTTP, включая поля и multipart framing |
| `LEAD_MAX_FORM_FIELDS` | `64` | Количество значений обычных полей, включая repeated values |
| `LEAD_MAX_FILES` | `10` | Документов в запросе |
| `LEAD_MAX_FILE_SIZE` | `10485760` (10 МиБ) | Размер каждого документа |
| `LEAD_MAX_TOTAL_FILE_SIZE` | `26214400` (25 МиБ) | Общий размер документов |

`config.settings.test` отключает лимитер по умолчанию, чтобы обычные изолированные
тесты не делили файл/лимит; целевые tests_protection включают собственное временное
хранилище. Для локального сайта используйте local settings и SQLite override,
если PostgreSQL отсутствует, и явно включите лимитер. Не переносите test settings,
тестовый ключ и тестовую БД в production.

Пример серверного окружения при TCP loopback:

```dotenv
LEAD_RATE_LIMIT_ENABLED=true
LEAD_RATE_STORE=/var/lib/energy-ecosystem/lead-limits/limits.sqlite3
LEAD_TRUSTED_PROXY_NETWORKS=127.0.0.1/32,::1/128
LEAD_TRUST_UNIX_SOCKET_PROXY=false
```

Оператор создаёт закрытый каталог с владельцем web user (например, режим `0700`),
задаёт umask `0077` сервису и проверяет возможность создания SQLite-файла и journal.
Приложение намеренно не создаёт произвольный родительский каталог. Файл не должен
совпадать с application DB. Worker уведомлений не использует этот файл/лимитер.

## Адрес клиента и nginx → Gunicorn

При **прямом локальном TCP запуске** оставьте список proxy пустым и Unix opt-in
выключенным. Используется `REMOTE_ADDR`; произвольные `X-Real-IP` и
`X-Forwarded-For` игнорируются. IPv4-mapped IPv6 нормализуется к IPv4, чтобы не
создавать второй bucket.

За **доверенным nginx по TCP** разрешите только фактические адреса nginx peers в
`LEAD_TRUSTED_PROXY_NETWORKS`. nginx обязан **перезаписывать**, а не добавлять:

```nginx
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

Приложение использует единственный корректный IP из `X-Real-IP` только от
доверенного peer. `X-Forwarded-For` не используется вообще. Отсутствующий или
некорректный X-Real-IP у доверенного nginx даёт 503 до разбора тела; приложение
не объединяет посетителей под IP proxy. Неверный/пустой прямой peer также даёт 503.
System check отклоняет некорректные CIDR и сети `/0`.

При **Unix socket Gunicorn** `REMOTE_ADDR` может быть пустым. Установите
`LEAD_TRUST_UNIX_SOCKET_PROXY=true` только если web слушает исключительно закрытый
socket и его permissions допускают только nginx/доверенных локальных пользователей.
При пустом peer тогда требуется корректный перезаписанный X-Real-IP; иначе 503.
TCP peer от этой настройки доверенным не становится. Не используйте Unix opt-in
как обход неправильной конфигурации proxy.

Gunicorn должен быть доступен только nginx (закрытый socket или private loopback),
иначе посетитель может попасть в обход nginx и его ограничений. Не доверяйте всем
сетям или пользовательским proxy headers. Если перед nginx появится CDN/LB,
отдельно настройте nginx real_ip только для проверенных адресов этого upstream:
без этого `$remote_addr` станет общим адресом LB. Это не настройка доверия к
произвольному XFF клиента.

## Загрузки: что и когда ограничивается

Контракт: repeated `attachments`, до 10 непустых файлов, каждый ≤10 МиБ, сумма
≤25 МиБ. Legacy `attachment` допускает один документ по тем же ограничениям;
смешивать оба способа нельзя. Неизвестное файловое поле и repeated legacy
`attachment` отклоняются. Сервер проверяет контракт независимо от frontend.

1. После IP-допуска `Content-Length > 27 МиБ` даёт **413** до parser.
2. Обёртка stream считает фактически прочитанные байты; превышение общего тела
   даёт 413 даже при недостоверном малом заголовке, если тело доступно WSGI parser.
   Gunicorn/nginx должны обеспечивать корректное HTTP framing; приложение не
   заменяет их защиту от request smuggling.
3. Endpoint-specific upload handler стоит **перед** Django memory/temp handlers.
   При начале файла он проверяет имя поля и количество; на чанках ≤64 КиБ — размер
   файла и общую сумму; на завершении — пустой файл. Недопустимый чанк не передаётся
   storage handler. Ранее допустимая часть большого файла может уже находиться во
   временном файле, но **весь** недопустимый файл не сохраняется. Размер parser
   read-ahead ограничен чанками; фактический HTTP поток nginx мог уже буферизовать.
4. Django дополнительно применяет штатные ранние parser ceilings:
   `DATA_UPLOAD_MAX_NUMBER_FIELDS` (по умолчанию 1000),
   `DATA_UPLOAD_MAX_NUMBER_FILES` (100) и non-file
   `DATA_UPLOAD_MAX_MEMORY_SIZE` (2,5 МиБ). Файловый handler обеспечивает более
   строгие 10 реальных документов. Для игнорируемых multipart частей без валидного
   filename остаются общие Django ceilings и общий byte budget.
   Endpoint ceiling **64 обычных значения** проверяется после bounded parse, до
   serializer/fingerprint/DB. Это не ранний счётчик каждого multipart поля;
   до этой проверки parser может обработать до штатного Django ceiling.
   Настройки глобального parser не изменены и не сужают admin.
5. `FILE_UPLOAD_MAX_MEMORY_SIZE` (штатно 2,5 МиБ) — **порог выбора memory/temp
   handler**, не запрет размера документа. Корректные 10 МиБ проходят через temp.
   В production обеспечьте закрытый `FILE_UPLOAD_TEMP_DIR` и свободное место.
6. Существующая `_validate_attachments` остаётся вторым барьером перед fingerprint
   и private storage. При ранних/поздних parser отказах закрываются текущие и уже
   завершённые uploads; temporary files удаляются. Lead, LeadAttachment и job не
   создаются. Существующий transactional cleanup storage остаётся без изменений.

Файловые нарушения сохраняют прежний **400**, общий body ceiling — **413**.
Исключения штатного parser ceilings превращаются в безопасный 413. nginx может
вернуть HTML 413/429. Поля обычной заявки занимают значительно меньше запаса 2 МиБ;
реальный multipart с документами ровно 25 МиБ проверяется тестом.

## nginx-шаблон и ответы

См. `ee_site/deploy/nginx_lead_request_protection.conf.example`. Это пример для
ручного объединения с существующим конфигом, не конфигурация действующего сервера.
`map` и zones идут в `http {}`, exact location — в существующий `server {}`.
Прочие locations, TLS, admin и закрытое private storage сохраняются.

Zones общие для nginx workers. Ключ заполнен только для POST: прочие методы не
потребляют rate bucket. Short zone: 20r/m, burst 19, nodelay; sustained zone: 2r/m,
burst 20, nodelay. Это nginx leaky bucket, **не** точные скользящие 20/60 и 100/3600;
точный app-лимит остаётся в Django. При превышении nginx отвечает 429 до Django;
он не задаёт выдуманное время ожидания. `client_max_body_size 27m` оставляет запас
к допустимым 25 МиБ. Body timeout ограничивает паузу чтения, а не общую длительность
загрузки. Request buffering включён: ограничены bytes, но до app-проверки nginx
может принять тело целиком и использовать свой temp storage.

App 429: JSON `{detail, code: "lead_rate_limited", retry_after: <секунды>}` и
`Retry-After`. Ожидание — округлённый вверх максимум времени до допуска обоих окон;
новые попытки того же IP могут увеличить фактическое ожидание после ответа.
503 не выдаётся за 429 и не содержит выдуманного retry time. Ответ не раскрывает IP,
имена документов, DB paths или персональные данные.

Frontend распознаёт JSON/HTML 429 и 413. При 429 показывает ожидание из числового
Retry-After/JSON либо сообщение «немного подождите». На отказе форма не сбрасывает
поля, документы или существующий submission_id. POST не повторяется автоматически;
посетитель повторяет вручную. При изменении данных/файлов действует прежний
signature/UUID механизм. Внешний вид LeadForm не менялся.

## Проверки

Из `ee_site/backend` (активируйте установленный venv):

```sh
python manage.py test --settings=config.settings.test --noinput
python manage.py check --settings=config.settings.test
python manage.py makemigrations --check --dry-run --settings=config.settings.test
```

Из `ee_site/frontend`:

```sh
npm test
npm run build
npm run lint
```

Из корня репозитория: `git diff --check`.

Целевые backend-тесты используют отдельные временные SQLite/private/temp paths,
проверяют burst/sustained, expiry, независимость клиентов, spoofed headers,
trusted TCP/Unix proxy, отказ до parser/fingerprint/create/job, fail-closed при
реальной блокировке SQLite, прямые multipart limits, пустые документы, cleanup,
реальные 25 МиБ, actual stream ceiling и идемпотентный повтор после ограничения.
Отдельный тест запускает **12 настоящих Python процессов** против одного SQLite:
при лимите 3 должны получить допуск ровно 3, остальные 9 — rate limit. Это не mock
межпроцессной проверки. Frontend-тесты проверяют JSON/HTML 429/413, одну попытку
POST, сохранность FormData/documents/ключа и ручной идемпотентный повтор.

PostgreSQL concurrency существующей очереди, Gunicorn topology и nginx template
нуждаются в проверке на staging. SQLite-process тест подтверждает только выбранный
single-host limiter. В облачном окружении nginx/PostgreSQL отсутствуют; production
БД, реальный SMTP и публичные адреса для проверок не используются.

## Короткий ручной чек-лист локальной формы

1. С локальной тестовой БД и console/locmem email включить лимитер, временно задать
   2 попытки/60 секунд; открыть форму, заполнить поля, выбрать документы.
2. Отправить обычную заявку: только подтверждённый 201/идемпотентный 200 показывает
   успех. В background-режиме проверить одну pending-запись без реального SMTP.
3. Повторными ручными отправками получить 429; проверить текст ожидания, заполненные
   поля, список документов, отсутствие success и автоматических запросов в Network.
4. Подождать окно и вручную повторить неизменённую заявку после имитированной сетевой
   ошибки/потерянного ответа: тот же UUID, прежний id, без второго файла/job.
5. В devtools/mock proxy вернуть HTML 429 и 413: понятная ошибка, поля и файлы
   остаются. Проверить пустой, 11-й файл, >10 МиБ и >25 МиБ прямым local multipart.
   После проверки восстановить 20/60 и 100/3600.

## Действия для будущего серверного внедрения

1. На staging уточнить TCP/Unix socket topology nginx → Gunicorn, фактические
   trusted peers; закрыть прямой доступ к Gunicorn и настроить overwritten headers.
2. Создать private local limiter directory/web ownership/umask и temp upload
   directory. Настроить LEAD_RATE_STORE одинаково всем workers, trusted TCP CIDR
   либо защищённый Unix opt-in. Проверить system check и 503 при ошибочной конфигурации.
3. Объединить nginx template с действующим конфигом, адаптировать upstream, выполнить
   `nginx -t`; только затем согласовать применение с перезапуском web workers.
   Проверить отсутствие доступа к private storage и limiter file.
4. На staging проверить клиентов через nginx, подменённые headers, 429/413 JSON/HTML,
   multipart 25 МиБ и одновременные обращения нескольких Gunicorn workers к общему
   файлу. Проверить форму браузером, включая потерянный ответ и сохранность UUID.
5. Сохранить текущий notification mode. Если background уже включён, оставить
   supervised worker с той же application DB/private storage; лимитер не создаёт
   новую очередь и не требует переключения mode. Согласовать worker по отдельной
   инструкции `lead-notification-worker.md`, проверить pending/sending и журналы.
6. Настроить мониторинг 429/503, SQLite lock timeouts, места в nginx/Django temp,
   private storage и глубины очереди; скорректировать лимиты по реальным офисным
   посетителям. Откат IP-защиты: `LEAD_RATE_LIMIT_ENABLED=false` с restart web и
   отдельно отключить nginx zones в endpoint; upload guards остаются включены.

Никакие merge/deploy или изменения действующего сервера этим этапом не выполняются.
