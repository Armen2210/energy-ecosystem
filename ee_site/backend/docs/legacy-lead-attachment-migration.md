# Перенос исторических вложений заявок

Команда `migrate_legacy_lead_attachments` переносит только документы из старого
`Lead.attachment`. Новые загрузки уже создаются как `LeadAttachment` в каталоге
`LEAD_PRIVATE_ATTACHMENT_ROOT`, которому storage намеренно не предоставляет URL.

## Подготовка и запуск

Перед будущим production-запуском отдельно остановите изменения выбранных заявок и
сделайте согласованные резервные копии:

1. дамп PostgreSQL со схемой и данными;
2. полный snapshot публичного media-хранилища с историческими файлами;
3. полный snapshot приватного `LEAD_PRIVATE_ATTACHMENT_ROOT`;
4. проверьте восстановление всех трех копий в изолированной среде.

Предпросмотр по умолчанию ничего не пишет ни в БД, ни в storage и не инициирует
уведомления:

```bash
python manage.py migrate_legacy_lead_attachments --limit 100
python manage.py migrate_legacy_lead_attachments --lead-id 42 --lead-id 57 --limit 2
```

Запись требует явного флага:

```bash
python manage.py migrate_legacy_lead_attachments --apply --limit 100
```

Обычный режим выбирает только еще не перенесенные заявки. Поэтому после успешной
партии следующий запуск автоматически переходит к следующим ID. Если ранняя
проблемная запись постоянно попадает в лимит, зафиксируйте ее для расследования и
продолжите следующей партией с `--after-id <последний-проверенный-id>`. Это не
помечает проблему успешной и не исключает ее из последующей проверки полноты.

Проверка уже созданных соответствий отделена от переноса и всегда read-only:

```bash
python manage.py migrate_legacy_lead_attachments --verify --limit 100
python manage.py migrate_legacy_lead_attachments --verify --after-id 1000 --limit 100
```

Она отдельно проверяет доступность и хеш старого источника, правильность связи
`legacy_source`/`lead`, наличие, размер и сохраненный SHA-256 приватной копии.
Повреждения дают ненулевой статус; скрытого ремонта и fallback на публичную ссылку
нет. Для полной проверки последовательно двигайте `--after-id` до пустой партии,
затем отдельно повторно проверьте отложенные проблемные ID через `--lead-id`.

Каждый запуск печатает только ID, код результата и итоговые счетчики `checked`,
`migrated`, `verified`, `skipped`, `problems`; имена, полные пути, содержимое и контактные
данные не журналируются. Любая незавершенная запись дает ненулевой exit status,
но не останавливает обработку остальных записей.

## Гарантии и проверка полноты

Источник сначала читается порциями. При копировании через storage API снова
вычисляется SHA-256, затем приватная копия повторно читается порциями. Запись
`LeadAttachment` появляется только при совпадении размеров и всех хешей.
`legacy_source` — уникальная ссылка на исходный `Lead`, поэтому имя или размер не
используются как признак завершения. Старое значение `Lead.attachment` и файл не
изменяются. Приложение показывает и отправляет проверенную приватную копию только
один раз, а публичную ссылку на старое поле в admin не выводит.

Повторяйте dry-run и apply партиями, пока обычный запуск не даст `checked=0`.
Затем пройдите все соответствия отдельными `--verify`-партиями и добейтесь
`problems=0`. Сопоставьте число непустых старых полей с числом строк, имеющих
`legacy_source`, и расследуйте расхождение в изолированной среде.

Apply-запуски сериализуются PostgreSQL advisory lock на весь процесс без длинной
транзакции: блокировка строки берется лишь перед фиксацией результата. Для SQLite
используется локальный файловый lock; он не является доказательством межсерверной
конкурентности. На платформе без поддерживаемого `fcntl` non-PostgreSQL apply
завершается до копирования; help, dry-run и PostgreSQL apply остаются переносимыми.
Обычный `threading.Lock` не используется. Изменение имени поля обнаруживается
перед commit, а изменение байтов во время копирования — сравнением хешей.

Тесты логики переноса на SQLite подменяют только контекстный менеджер блокировки,
чтобы одинаково выполняться на Windows и Unix. Отдельные тесты сохраняют проверку
выбора PostgreSQL-ветки и безопасного отказа SQLite при отсутствии `fcntl`.
Эти mock-проверки не являются доказательством реальной межпроцессной защиты;
такое доказательство требует отдельных конкурентных запусков на PostgreSQL.

## Ограничения, сбой и откат

DB и файловое storage не образуют общую атомарную транзакцию. При обычной ошибке
команда удаляет только созданную текущей попыткой и еще не связанную копию. При
`SIGKILL`, падении машины или потере storage после `save` может остаться файл с
префиксом `leads/attachments/legacy-<lead-id>-`, которого нет в колонке
`LeadAttachment.file`. Такой orphan следует **только обнаружить и сверить**
отдельным read-only инвентаризационным отчетом; эта команда намеренно не выполняет
общую очистку. Повторный запуск создаст новую проверенную копию.

Для отката переключения удалите только соответствующую строку `LeadAttachment`
после резервного копирования и проверки, что `Lead.attachment` и публичный файл
сохранены. Это вернет прежнее прикладывание исторического файла к уведомлению;
само значение старого поля при переносе не меняется. Уже отправленные письма и
служебные поля уведомлений команда не меняет.

**Важно:** копирование не закрывает публичный доступ к исходным файлам. Закрытие
nginx-раздачи и удаление исходников — отдельный последующий этап только после
проверки переноса и подготовленного отката.
